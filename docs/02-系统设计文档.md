## 1. 设计目标与约束

| 编号 | 设计目标 | 落地手段 |
| --- | --- | --- |
| D1 | 研究态与生产态同构 | 回测与实盘调用**同一份** `Strategy` 与 `RiskEngine`，仅 `DataSource` / `BrokerAdapter` 实现不同 |
| D2 | 引擎与业务解耦 | `engine/` 为纯计算内核，零 Web / 零 DB 依赖，可 `python -m` 直接跑回测 |
| D3 | 一切可回溯 | 数据快照版本、策略 git commit、信号→订单→成交全链路 ID 串联 |
| D4 | 单机可运行 | 无 K8s、无消息队列中间件（用 SQLite/Redis + 进程内事件总线即可） |
| D5 | 策略崩不影响系统 | 策略运行于受限上下文，异常捕获后自动停仓并告警 |
| D6 | 风控不可绕过 | 所有出单必须经 `RiskEngine` + `OrderRouter`，策略层拿不到 Broker 句柄 |

**核心不变量（Invariants）**：任何一条真实委托，其 `order_id` 必须能反查 `signal_id` → `strategy_version` → `factor_snapshot_date`。这是安全审计与故障复盘的根基。

> 原设计里的 `engine/execution/`（`oms.py`/`router.py`/`adapters/`）在实现时拆成了
> `engine/trade/`（订单管理与账本）与 `engine/broker/`（券商适配器）两处：
> 订单生命周期与券商通道是两类不同的关注点，混在一个包里会让"幂等键归谁管"这类问题说不清。
> 调度同样没有采用 `app/scheduler/ + APScheduler` 常驻进程，而是
> `app/schedule_cli.py` + `schedule_service`：外部调度器每天调一次，进程跑完即退出，
> 对单人模拟盘而言更简单、也更容易排查（退出码即契约）。

> 说明：原设计曾把 `pyproject.toml` 放在 `backend/` 下，但 `engine/` 位于仓库根，
> 单 Python 项目无法这样组织（会出现两个工程根），故统一为「仓库根即工程根，
> `app` 与 `engine` 平铺」。分层约束不靠目录层级、而靠依赖方向检查与代码评审保证。

## 3. 核心领域模型（`engine/types.py`）

统一使用 `dataclass(frozen=True, slots=True)`，价格与金额用 `Decimal`（避免浮点误差累积），数量用 `int`。

| 模型 | 关键字段 |
| --- | --- |
| `Bar` | `code, dt, open, high, low, close, volume, amount, limit_up, limit_down, is_suspended, adj_factor` |
| `Signal` | `signal_id, strategy_id, trade_date, code, direction(BUY/SELL/HOLD), score, target_weight, reason, factor_snapshot` |
| `OrderPlan` | `plan_id, strategy_id, trade_date, code, side, target_qty, limit_price, urgency, status` |
| `Order` | `order_id, plan_id, broker_order_id, code, side, qty, price, filled_qty, avg_price, status, reject_reason, idem_key, created_at` |
| `Trade` | `trade_id, order_id, code, side, qty, price, fee, trade_time` |
| `Position` | `account_id, code, qty, avail_qty, frozen_qty, avg_cost, last_price, market_value, unrealized_pnl` |
| `Account` | `account_id, total_asset, cash, available_cash, frozen_cash, market_value, nav, trade_date` |
| `RiskDecision` | `passed, rule_hit, action(PASS/REJECT/SHRINK/HALT/FLATTEN), adjust_qty, message` |

`Order.status` 状态机（唯一合法迁移）：

```
PENDING ──► SUBMITTED ──► PARTIAL ──► FILLED
   │            │            │
   │            └────────────┴──► CANCELED
   └──► REJECTED（风控/资金/合规拒单，终态）
```

## 4. 关键抽象（端口与适配器，`engine/ports.py`）

```python
class DataSource(Protocol):
    def daily(self, codes: list[str], start: date, end: date, adj: str = "post") -> pd.DataFrame: ...
    def minute(self, codes: list[str], start: datetime, end: datetime) -> pd.DataFrame: ...
    def calendar(self) -> list[date]: ...
    def universe(self, index_code: str, on: date) -> list[str]: ...
    def financial(self, codes: list[str], ann_date_to: date) -> pd.DataFrame: ...

class BrokerAdapter(Protocol):
    def connect(self) -> None: ...
    def query_asset(self) -> Account: ...
    def query_positions(self) -> list[Position]: ...
    def place(self, order: Order) -> str: ...          # 返回 broker_order_id，必须幂等
    def cancel(self, broker_order_id: str) -> bool: ...
    def on_order_update(self, cb: Callable[[Order], None]) -> None: ...
    def on_trade_update(self, cb: Callable[[Trade], None]) -> None: ...

class Strategy(Protocol):
    def init(self, ctx: Context) -> None: ...                 # 读取参数、预加载数据
    def on_bar(self, ctx: Context, bars: dict[str, Bar]) -> list[Signal]: ...
    def on_order_filled(self, ctx: Context, trade: Trade) -> None: ...
```

`Context` 是策略唯一的对外通道，提供 `history()` / `factor()` / `positions()` / `account()` / `bars()` / `universe()`，**不提供下单方法**——下单只能通过返回 `Signal` 由引擎统一走风控与执行。这是 D6 的技术保障，且有守护测试（`tests/test_ports.py`）断言 `Context` 上不出现任何 `place/buy/sell/cancel/order` 方法，防止后来者图方便往上下文里加下单接口。

风控侧同样是端口化：`PreTradeRiskRule.check(RiskContext)` 处理逐条订单计划（事先校验/缩量），`IntradayRiskRule.check_portfolio(PortfolioSnapshot)` 处理组合级触线（只平不开/清仓），两类规则各自独立演进。

**批量行情的类型口径**：端口上统一用 `pandas.DataFrame`（akshare/tushare/券商导出原生均为 pandas，边界层零转换成本），因子与回测的热点计算再转 Polars/NumPy 向量化（见 §5.6）。列名一律取自 `engine.datahub.schema`，禁止各处硬编码字符串。

## 5. 回测引擎设计（核心）

### 5.1 时间轴与事件循环

```
for dt in trading_days(start, end):
    bus.emit(MARKET_OPEN, dt)
    for bar_dt in intraday_steps(dt, freq):          # 日频则单步
        bars = datahub.bars_at(bar_dt)               # 已过滤停牌
        bus.emit(BAR, bars)

        # 1) 策略产信号（严格用 bar_dt 及之前的数据）
        signals = strategy.on_bar(ctx, bars)

        # 2) 组合构建 → 订单计划
        plans = portfolio.build(signals, account, positions)

        # 3) 风控前置
        decisions = risk.pre_trade(plans, account, positions, bars)

        # 4) 撮合（成交价 = 下一 bar 开盘价 or 本 bar 收盘价，可配）
        fills = matcher.match(decisions, bars, next_bars)

        # 5) 结算：费用、持仓、资金、净值快照
        account.settle(fills, dt)
        bus.emit(MARKET_CLOSE, dt)
```

**防未来函数的三条硬规则**：
1. `datahub` 只允许返回 `dt` 及之前的数据，越界直接抛异常而非静默截断；
2. 财务数据必须按 `ann_date <= dt` 过滤（不能用 `report_date`）；
3. 信号 → 成交强制错开至少一个 bar（`fill_delay` 默认 1），杜绝「同一 bar 收盘算价、同一 bar 成交」。

### 5.2 撮合器（`match.py`）

| 场景 | 处理 |
| --- | --- |
| 停牌 `is_suspended` | 不成交，订单保留至复牌 |
| 买入价 ≥ `limit_up` 且当日封板 | 视为无法成交（一字板场景），订单转入顺延队列 |
| 卖出价 ≤ `limit_down` 且当日封板 | 同上 |
| 计划数量 > 当日成交量 × `max_vol_ratio`(默认 10%) | 只成交上限部分，余量顺延至下一 bar |
| 限价单价格未被价格区间覆盖 | 部分成交或不成交 |
| 顺延超过 `max_delay_days`(默认 2) | 撤销并记录 `expired` |

撮合价可选：`open`（默认，最贴近实盘挂单）/ `close` / `vwap` / `mid`。

### 5.3 成本与滑点模型（`cost.py` / `slippage.py`）

```python
# cost.py
commission = max(amount * 0.0003, 5.0)        # 万 3，最低 5 元
stamp_tax  = amount * 0.001 if side == SELL else 0   # 印花税卖出千 1
transfer   = amount * 0.00001                  # 过户费
total_fee  = commission + stamp_tax + transfer

# slippage.py —— 可插拔
FixedBpsSlippage(bps=5)                        # 成交价 ±5bp
VolumeImpactSlippage(k=0.1)                    # price * (1 + k * sqrt(qty / adv))
```

### 5.4 复权处理（易错点，单独约定）

- 回测内部计算（持仓市值、因子、信号）统一使用**后复权价**，保证跨除权日收益连续；
- 下单前必须用 `adjust.py` 将后复权价**还原为真实价**，并按最小价格单位 `0.01` 取整后校验涨跌停；
- 报告展示用**前复权**净值曲线。三者职责分离，禁止混用。

### 5.5 绩效与归因（`metrics.py` / `attribution.py`）

> **落地情况（2026-10-15）**：`metrics.py` 已实现（总收益/年化/波动/最大回撤含起止日期/夏普/
> 索提诺/卡玛/日胜率/盈亏比/月度收益表 + 可选基准的 alpha/beta/信息比率/跟踪误差）；
> `attribution.py`（收益归因）**未实现**。

- 指标：总收益、年化、最大回撤及区间、夏普、卡玛、索提诺、胜率、盈亏比、年化换手、Alpha/Beta、信息比率、跟踪误差（公式见需求文档附录 A）；
- 归因：Brinson 行业归因（配置 + 选股）、因子暴露归因、个股贡献 Top20/Bottom20；
- 输出：`metrics.json` + `nav.parquet` + `trades.parquet` + `report.html`（ECharts 自包含）。

### 5.6 并行与性能

- 参数寻优：`ProcessPoolExecutor`，按参数组合切分，**共享只读数据**（内存映射 Parquet）；
- 因子计算：向量化（Polars），全市场 5000 只 × 10 年的单因子计算目标 ≤ 3s；
- 回测热路径避免 pandas 逐行操作，统一 Polars/NumPy 数组 + 预取窗口。

## 8. 风控引擎设计

> **落地情况（2026-10-15）：已实现**，见 `engine/risk/{rules,engine,kill_switch}.py`。
> 与本文设计的三处补充，都是实现时被测试逼出来的：
> 1. **缩量要沿规则链传递**：集中度缩到 1 万股后，后续规则必须按缩量后的数量判断，
>    否则"单笔金额上限"仍按原始数量算，规则之间互相失效；
> 2. **事中检查必须排在撮合之前**：早上就已知昨日收盘的回撤，降级当天就不该再买；
>    排在撮合之后会让"降级"晚一天生效；
> 3. **降级要同时撤回未成交的买单**：只拦新计划不够——昨天挂出的买单今天照样成交。
> 急停开关另有与交易门禁**相反**的默认值：门禁文件缺失→关闭（不许交易），
> 急停文件缺失→未激活（紧急制动不该默认踩着），但两者读取异常时都倒向安全侧。

### 8.1 执行位置

```
Signal → Portfolio → OrderPlan
                        │
                ┌───────▼────────┐
                │  RiskEngine    │  事前：逐 plan 校验
                │  pre_trade()   │  ├ 黑名单        (REJECT)
                └───────┬────────┘  ├ 单票/行业/总仓位 (SHRINK)
                        │           └ 可用资金/可用持仓 (SHRINK/REJECT)
                  OrderRouter
                        │
                   BrokerAdapter
                        │
   ┌────────────────────▼────────────────────┐
   │ RiskEngine.intraday()  事中：定时轮询      │
   │  ├ 单日亏损阈值 → HALT（禁止开仓）         │
   │  ├ 单日亏损硬线 → FLATTEN（清仓熔断）      │
   │  ├ 组合回撤阈值 → 降仓/清仓               │
   │  └ 撤单率/下单频率异常 → HALT             │
   └───────────────────────────────────────────┘
```

### 8.2 规则接口

```python
class RiskRule(Protocol):
    name: str
    priority: int                                   # 数值小者先执行
    def check(self, ctx: RiskContext) -> RiskDecision: ...
```

规则链按 `priority` 顺序执行，任一返回 `REJECT` 立即短路；`SHRINK` 会改写 `qty` 后继续传递给后续规则（保证「单票上限」与「资金校验」两级缩量叠加正确）。

### 8.3 风控状态机

`NORMAL → WARN（告警）→ HALT（只平不开）→ FLATTEN（强制清仓）`，降级单向，人工在控制台确认后才可恢复 `NORMAL`，每次状态变更写 `audit_log`。

### 8.4 急停

`POST /api/v1/risk/emergency-stop`：加 Redis 分布式锁 → 通知所有策略停止产信号 → 撤销全部未成委托 → 可选市价清仓 → 落审计。要求 1s 内生效（Redis 标志位轮询间隔 200ms）。

## 9. OMS 与执行设计

> **落地情况（2026-10-15）：已实现（模拟盘）**，见 `engine/trade/oms.py`（订单管理）、
> `engine/trade/ledger.py`（账本持久化）、`engine/broker/paper.py`（模拟盘券商）。
> 三处与设计的差异：
> 1. **拆成两个包**：订单生命周期（trade）与券商通道（broker）分开，避免"幂等键归谁管"说不清；
> 2. **幂等键用业务要素确定性推导**（`策略|日期|代码|方向|数量`），而不是随机的计划号——
>    进程重启后随机号会变，幂等键随之失效，同一笔单会被重复报出；
> 3. **通道异常标记 UNKNOWN 而非重报**：重报可能造成真实重复委托，必须走查单校准；
>    `reconcile()` 以券商全量委托为准纠正本地账本，本地有而券商没有的判为废单。
> 「断线后每 30s 主动全量校准」尚未做成定时器，目前由盘后调度链的 `reconcile` 步骤承担。

| 组件 | 职责 | 关键点 |
| --- | --- | --- |
| `oms.py` | 订单全生命周期、持仓与资金的内存态账本 | 每次事件后与 DB 落库；重启后从 DB 重建状态 |
| `router.py` | 按 `urgency` 路由到拆单器与适配器 | 单票小额直发；大额按 TWAP 拆 |
| `splitter.py` | TWAP / VWAP / 等量拆分 | 拆单结果仍共用同一 `plan_id`，便于聚合统计 |
| `reconciler.py` | 盘后对账 | 本地 vs 券商持仓/资金逐项比对，差异 > 阈值 → 告警并锁定次日交易 |

**幂等下单**：`idem_key = hash(plan_id + broker_order_id_seq + trade_date)`，`order` 表 `uk_idem_key` 唯一约束；网络超时重试先查库，已存在则直接返回，绝不重复报单。

**断线恢复**：`on_order_update` 回调丢失时，每 30s 主动 `query_orders()` 全量校准一次状态。

## 10. 调度设计

> **落地情况（2026-10-15）：已实现简化版**，见 `app/services/schedule_service.py` + `app/schedule_cli.py`。
> 当前只有两条任务链（`pre`：同步 → 质量校验 → 门禁；`post`：模拟盘 → 查单校准），
> 由外部调度器（Windows 任务计划 / cron）每天调用，**不引入 APScheduler 常驻进程**——
> 对单人模拟盘而言更简单也更好排查，退出码（0/1/3）就是调度契约。
> 日内高频任务（`calc_factor` / `gen_signal` / `intraday_risk`）尚未实现：它们依赖盘中行情与实时风控采样。
>
> 三条实现时的语义修正（都属于"把正常当异常"）：
> 1. **交易日守卫以数据源为准**：本地日历等于"行情里出现过的日期"，而盘前今天的数据本就不存在，
>    用它会把今天判成非交易日 → 盘前任务永不触发、数据永远同步不了（死锁，实测踩到过）；
> 2. **幂等空转不算失败**（本地已是最新时同步会跳过）——否则定时任务每天误告警；
> 3. **质量 FAIL 不算调度失败**：检查执行成功、结论是不该交易，门禁已拦住；
>    但**同步失败不阻断质量校验**，否则门禁会停在旧状态。

| 任务 | 时点 | 前置依赖 | 失败后果 |
| --- | --- | --- | --- |
| `sync_data` | 09:00 | 无 | **禁止当日交易** |
| `check_quality` | 09:10 | sync_data | **禁止当日交易** |
| `calc_factor` | 09:15 | check_quality | **禁止当日交易** |
| `gen_signal` | 09:20 | calc_factor | **禁止当日交易** |
| `build_plans` | 09:25 | gen_signal | 仅告警 |
| `execute` | 09:35 / 14:30 | build_plans | 告警 + 重试 3 次 |
| `intraday_risk` | 每 30s（盘中） | execute | 告警 |
| `settle` | 15:05 | execute | 告警 |
| `reconcile` | 15:20 | settle | **锁定次日交易** |
| `daily_report` | 15:30 | reconcile | 告警 |
| `nightly_jobs` | 20:00 | - | 仅告警 |

所有任务以**交易日历守卫**包裹（`is_trade_day(now) or skip`），并写入 `task_log`（入参、出参摘要、耗时、异常栈）。关键任务采用「前置依赖检查 + 不满足则跳过并告警」策略，避免出现「数据没更新却照常下单」这种最致命故障。

## 13. 错误处理与降级矩阵

| 故障 | 检测方式 | 处理 | 人需介入 |
| --- | --- | --- | --- |
| 数据源不可用 | 同步任务异常 | 重试 3 次（退避）→ 仍失败则禁止当日交易 | 是 |
| 数据质量 FAIL | 质量校验 | 禁止当日交易 + 告警 | 是 |
| 券商接口断连 | 心跳 / 下单异常 | 自动重连；未确认订单标记 `UNKNOWN` 并查单校准 | 是 |
| 下单被拒（资金/涨跌停） | 回报 | 记录 `reject_reason`，当日不再重试该标的 | 否 |
| 策略进程崩溃 | 沙箱捕获 | 停止该策略 + 撤销其未成委托 + 告警，其他策略不受影响 | 是 |
| 服务重启 | 启动流程 | 从 DB 恢复订单/持仓 → 与券商对账 → 校平后才允许交易 | 否 |
| 对账不平 | 盘后对账 | 锁定次日交易 + 告警 | 是 |
| 风控熔断 | 规则触发 | HALT / FLATTEN + 强告警 | 是 |

原则：**宁可当日不交易，不可带着未知状态交易**（fail-safe 优先于 fail-open）。

### 14.1 必须通过的引擎正确性用例（回归测试集，防未来函数与规则失真）

| 用例 | 断言 |
| --- | --- |
| T+1 限制 | 当日买入持仓 `avail_qty == 0`，策略当日卖出请求被拒 |
| 涨停不可买 | 一字板日买入订单不成交且在顺延队列，直到开板 |

| 停牌 | 停牌期间无成交，复牌后按复牌价成交 |
| 成本计算 | 给定成交额，手续费/印花税/过户费与公式逐项一致 |
| 滑点 | `FixedBpsSlippage(5)` 下成交价 = 基准价 ± 5bp |
| 成交量约束 | 下 1000 万、当日成交 5000 万（10% 上限 = 500 万），实际成交 500 万 |
| 复权连续性 | 除权日前后持仓市值无跳变，下单价格与真实盘口一致 |
| 未来函数 | 故意让策略读 `dt+1` 数据 → 引擎抛出越界异常 |
| 财务对齐 | `ann_date > dt` 的财报数据不可见 |
| 幂等下单 | 同一 `idem_key` 重复调用只产生 1 笔委托 |
| 风控不可绕过 | 直接构造超限 `OrderPlan` → 被裁剪为上限数量 |

| 新增市场（港股/美股） | 新增 `MarketRule` 实现（交易时段、T+0/T+1、涨跌幅、税费），引擎按 market 注入 |
| 因子挖掘/AI | 产出因子表达式后走既有 `factor/evaluate.py`，无需改动其他模块 |
